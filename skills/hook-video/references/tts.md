# 配音与时间戳

钩子视频没有人声原片，配音是新建资产：先确定路线，再拿时间戳，最后让动画跟着声音走。

## 路线 A：TTS 合成

1. 读主 Skill `.env` 是否已配置 TTS（模型名、音色等键）。未配置时列出缺项，让用户补充或改走路线 B/C；不把无声版说成已完成配音。
2. 首次使用一个 TTS 配置时，先用一句短文本做真实合成并保存音频与请求参数，记录模型、音色、采样率与实测时长；验证通过后再合成全篇。付费调用失败不盲目重复提交。
3. 全篇按句合成或整篇合成后切句，统一采样率与响度，句间留白按 `style.json` 的节奏定调。

## 语速与节奏（先量本机，再定档）

成片节奏由语速与气口共同决定，不是屏数。用户说"太快／太慢"，先量再调。

- **先做一次实测，不要信表格**。同一段文本分别用默认、`speech_rate=1.5`、`speech_rate=2.0` 合成，用 ffprobe 量时长换算字/秒。本机 qwen3-tts-flash + Cherry + 中文的实测值：

  | 参数 | 实测语速 |
  |---|---|
  | 默认 | 4.78 字/秒 |
  | `speech_rate=1.5` | 4.52 字/秒 |
  | `rate=1.5`（错误参数名） | 4.57 字/秒 |
  | `speech_rate=2.0` | 4.89 字/秒 |

- **结论：该端点上 `speech_rate` 基本不生效**（1.5–2.0 只在 4.5–4.9 字/秒之间抖动，且 1.5 反而略慢）。曾经把它写成"1.5 → 6.9 字/秒"是按字数估算而非实测，已作废。**不要靠反复重合成来提速**，那是付费且无效的循环。
- `parameters.rate` / `parameters.speed` 同样不生效（不报错也不改变语速）。参数名保留 `speech_rate`，但别指望它。
- **真正有效的提速手段是收紧气口**（下节）。实测：同一段文本 4.78 字/秒里，发声占比只有约 78%，其余是标点停顿；压缩停顿后有效语速提升约 15%，发音完全不变。
- 若收紧后仍显著慢于参考片，再考虑：换更快的音色／模型（`qwen3-tts-instruct-flash` 可用 `instructions` 控语气），或删文案。**删文案优先于继续压气口**——压到 0.08s 以下会听出赶。
- 参考片对齐：先量参考片语速（正文字数 ÷ 末词时间，字/秒），再反推本文案应有长度。参考片的"快"通常来自更高语速与更密画面，不是屏数更少。
- 参考片有真人原声时，用主 Skill 的 ASR 转写它，直接得到参考语速与句间气口，比按字数估算可靠。
- **屏数与快慢无关**：一条 30.7s 参考片也只有 5 个 ASR 语句单元、8 个画面话题。语速调到位后不要再为"显得快"拆更多屏。

## 收紧气口（整篇 TTS 后的必做步骤）

整篇合成的 TTS 会在**每个标点**留下 0.3–0.9s 停顿。一条 50s 的片子实测能有 10s 以上是静音（本机实例：51.36s 音频里 28 段停顿共 11.4s，占 22%），这是"节奏太慢"的头号来源，先处理它再谈排版。

```powershell
python scripts/compress_pauses.py --media voiceover.wav --transcript asr/transcript.source.json --out voiceover.tight.wav --out-transcript asr/transcript.tight.json --ffmpeg <ffmpeg.exe>
```

做法与要求：

- 用 `silencedetect`（建议 `noise=-38dB:d=0.18`）测出真实停顿区间，**不要用固定阈值猜**。
- 把超过 `--max-pause-s`（默认 0.25s）的停顿压到 `--keep-pause-s`（默认 0.08s）；短气口保留，避免赶。
- 同一次运行同时输出**重映射后的词级 JSON**：用同一张时间映射把每个词的新起止时间算出来。压缩音频与重排时间轴必须来自同一张映射，不能让音频和字幕各算一次。
- 收紧后**必须复验**：对紧凑音频再跑一次 `silencedetect`，并检查紧凑音频的时长与最后一段停顿的结束位置；两者对不上说明映射错了，不能直接进入排版。
- 收紧后再走常规回扫或直接用重映射结果；`production.json` 记录原始时长、收紧后时长与压缩量。
- 收紧是音频级处理，不改文本、不改发音，因此画面文字仍以用户原文为准。

## 路线 B：用户自配音

用户给了录音文件时，用主 Skill [asr.md](../../video-production/references/asr.md) 的百炼脚本对配音做词级转写，取得每句每词的时间码；配音本身不改写、不修音，文案与配音不一致时按用户确认的文本版本对齐。

## 路线 C：无配音版

明确标注为无声排版成片：每屏停留 = 正文字数 × 单字阅读系数（中文默认 0.30s，紧凑风格 0.22s，在 `style.json` 写明取值）+ 屏间缓冲 0.3s。此版本可以用 BGM 为主，但不补假配音。

## 指令控制（可选）

`qwen3-tts-flash` 不支持 `instructions`；需要自然语言指令控语气时要换 `qwen3-tts-instruct-flash`，参数名是 `instructions`（如"语速较快，语气笃定"）。换模型前先确认业务空间已开通该模型。

## 时间戳与动画同步

- 时间戳优先级：TTS 返回的句/字级边界 → ASR 回扫的词级时间 → 按句长均分（标注为推算，推算时间戳不驱动逐字动画）。
- 逐字打字机效果需要词/字级时间；只有句级时间时，打字机速率按该句字数均匀分配并在 `layout-plan.json` 标注来源。
- 每屏文字层开始帧 = 对应句配音起点；强调词点亮帧对齐该词的配音起点；所有秒→帧换算在生成 `layout-plan.json` 时统一舍入，组件内不再换算。
- 整句对齐用主 Skill 的 `align_script.py`，不要每次现写对齐代码（见下节）。

## 整句时间轴：用 align_script.py，不要手写对齐

脚本原文与 ASR 回扫结果必然有差异：数字读法（`7天` 被转写成 `七天`、`10个以上` 转写成 `十个以上`）、同音字（`进校`→`尽校`）、漏字（`已经`被吞成`已`）。手写一句一个 while 循环会反复翻车。

统一用：

```powershell
python scripts/align_script.py --script hook-script.json --transcript asr/transcript.source.json --out timing.json
```

它做三件事，并且**自带自检**：

1. 用段落级切分（`utterances`）先定大边界，再在带内做字符级对齐；
2. 代价模型是"限带 + 单删单插比同槽替换更便宜"，所以数字读法差异被吸收成一对 gap，而不是让整句滑到后面的近似短语上；
3. 逐句核对"匹配窗口的第一个字是否等于脚本第一个字"，不一致直接报错退出，不产出错误时间轴。

输出 `timing.json` 含每句 `start_s/end_s/char_lo/char_hi` 与 `findings`（逐条列出数字等价、同音改写、跳过的 ASR 字符）。**findings 必须人工过一眼**：数字等价可以直接接受，同音改写必须与脚本原文比对后接受，跳字数超过句长的 15% 说明对齐不可信，要改脚本分句重跑。

不要在业务脚本里再写一份对齐算法；也不要为了对齐去改写用户文案（画面文字与字幕始终以用户原文为准，ASR 只提供时间轴）。

## 音乐与音效

BGM 音量不盖配音（配音存在时音乐为衬底）；打字声、chip 点亮声等音效跟随对应动画帧，一条视频一到两种，按 `style.json` 的动画强度取舍。
